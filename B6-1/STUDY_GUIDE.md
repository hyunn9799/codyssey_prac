# Codyssey B5-1 — 카페 주문 관리 데이터베이스 학습 및 구두평가 가이드

## 1. 데이터베이스 설계 및 정규화

### Q1. 테이블을 왜 4개(customer, menu, orders, order_item)로 분리했나요?
- **데이터 중복 최소화 및 이상 현상(Anomaly) 방지**:
  - 만약 하나의 큰 테이블에 고객 정보, 메뉴 정보, 주문 내역을 모두 저장한다면, 같은 고객이 여러 번 주문하거나 한 번 주문할 때 여러 메뉴를 시킬 때마다 고객 이름/이메일, 메뉴 이름/가격이 반복 저장됩니다.
  - 이로 인해 고객 이메일이 변경될 때 모든 행을 수정해야 하는 **수정 이상(Update Anomaly)**, 고객이 주문을 취소하여 행을 지울 때 고객 정보까지 함께 삭제되는 **삭제 이상(Delete Anomaly)**, 주문이 없는 고객이나 아직 팔리지 않은 메뉴를 등록하기 어려운 **삽입 이상(Insert Anomaly)**이 발생합니다.
- **역할과 책임의 분리 (관심사 분리)**:
  - `customer`: 카페를 이용하는 고객 정보 관리 (1:N 주문의 주체)
  - `menu`: 판매 중인 메뉴 목록 및 기본 가격 관리
  - `orders`: 특정 시점에 특정 고객이 수행한 주문 단위(주문 번호, 일시, 상태) 관리
  - `order_item`: 하나의 주문 내에 포함된 개별 메뉴 품목 및 주문 당시 수량/단가 관리 (N:M 관계를 1:N 2개로 해소하는 교차/연결 테이블)

### Q2. 엑셀과 데이터베이스의 차이점은 무엇인가요?
- **무결성 제약조건(Data Integrity)**: RDBMS는 PK(기본키), FK(외래키), NOT NULL, UNIQUE, CHECK 등의 강력한 제약조건을 데이터베이스 엔진 레벨에서 강제하여 잘못된 데이터(예: 음수 가격, 존재하지 않는 고객의 주문 등)의 유입을 원천 차단합니다.
- **트랜잭션(ACID)**: 다수의 작업이 하나의 원자적 단위로 실행되도록 보장(원자성, 일관성, 격리성, 지속성)하여 시스템 장애나 동시 수정 시 데이터 정합성을 유지합니다.
- **동시성 제어 및 대용량 데이터 처리**: 수많은 사용자가 동시에 읽고 쓰는 환경에서도 락(Lock)과 MVCC를 통해 안전하고 빠른 처리를 지원하며, 인덱스(B-Tree)를 통해 수천만 건의 데이터도 효율적으로 검색합니다.

## 2. 관계 및 키(Key) 개념

### Q3. PK와 FK의 역할 및 1:N 관계의 도메인 의미
- **PK (Primary Key, 기본키)**:
  - 테이블 내의 각 행을 고유하게 식별하는 유일한 값(고유성 + NOT NULL).
  - 예: `customer.customer_id`, `orders.order_id`
- **FK (Foreign Key, 외래키)**:
  - 다른 테이블의 기본키를 참조하여 두 테이블 간의 관계를 맺어주는 컬럼.
  - 참조 무결성(Referential Integrity)을 보장하여, 부모 테이블에 존재하지 않는 값을 자식 테이블에 넣지 못하게 차단합니다.
- **도메인 내 1:N 관계 의미**:
  1. `customer (1) : orders (N)`: 한 명의 고객은 여러 번 주문할 수 있지만, 특정 주문은 반드시 한 명의 고객에게 귀속됩니다.
  2. `orders (1) : order_item (N)`: 하나의 주문 영수증 안에는 여러 개의 주문 메뉴 품목이 포함될 수 있습니다.
  3. `menu (1) : order_item (N)`: 하나의 메뉴는 여러 주문의 상세 품목으로 판매될 수 있습니다.

## 3. 데이터 타입 및 제약조건 설계 근거

### Q4. 컬럼 타입을 이렇게 선정한 이유는 무엇인가요?
- **금액 (`price`, `unit_price`) -> `DECIMAL(10, 2)`**:
  - `FLOAT`나 `DOUBLE`과 같은 부동소수점 타입은 근사치를 저장하므로 금융/결제 계산 시 미세한 오차가 발생할 수 있습니다. 반면 `DECIMAL`은 고정소수점 타입으로 정확한 금액 계산을 보장합니다.
- **주문 일시 (`ordered_at`) -> `DATETIME`**:
  - 주문이 일어난 정확한 년-월-일 시:분:초를 저장하기 위해 사용합니다.
- **주문 상태 (`status`) -> `VARCHAR(20)` + `CHECK (status IN ('PAID', 'PENDING', 'CANCELLED'))`**:
  - 유효한 주문 상태 값만을 엄격하게 제한하여 데이터 오염을 방지합니다.
- **이력 관리 (`order_item.unit_price`)**:
  - 메뉴 가격(`menu.price`)이 나중에 인상되더라도, 과거 주문 당시의 결제 단가는 변하지 않아야 하므로 `order_item` 테이블에 주문 시점의 `unit_price`를 스냅샷 형태로 별도 보관합니다.

## 4. 인덱스 (Index) 및 성능 최적화

### Q5. 인덱스를 어떤 컬럼에 걸었고, 왜 그 컬럼이어야 하나요?
- **인덱스 대상 컬럼**: `orders(ordered_at)` (`idx_orders_ordered_at`)
- **선정 이유**:
  - 카페 주문 시스템에서 가장 빈번하게 발생하는 조회 패턴은 "오늘의 주문 내역", "특정 기간(이번 달) 매출 조회", "최신 주문순 정렬(`ORDER BY ordered_at DESC`)"입니다.
  - `ordered_at` 컬럼에 B-Tree 인덱스를 생성하면 테이블 전체를 탐색(Full Table Scan)하지 않고도 범위 검색(Range Scan)과 정렬 작업을 빠르게 수행할 수 있어 조회 성능이 획기적으로 개선됩니다.

## 5. SQL 쿼리 및 핵심 개념

### Q6. INNER JOIN과 LEFT JOIN의 차이는 무엇인가요?
- **INNER JOIN (교집합)**:
  - 두 테이블 모두에 조인 조건이 일치하는 행만 반환합니다.
  - 예: `Q05`에서 주문 이력이 있는 고객과 주문만 조회됩니다.
- **LEFT JOIN (기준 테이블 전체 + 매칭 데이터)**:
  - 왼쪽 테이블의 모든 행을 반환하며, 오른쪽 테이블에 매칭되는 데이터가 없으면 `NULL`로 채웁니다.
  - 예: `Q08`에서 주문을 한 번도 하지 않은 신규/휴면 고객(`customer_id = 12`)도 결과에 포함되며, 주문 관련 컬럼은 `NULL`로 표시됩니다.

### Q7. GROUP BY와 집계 함수(COUNT, SUM, AVG)는 어떻게 동작하나요?
- **GROUP BY**: 지정한 컬럼(예: 카테고리, 고객번호 등)의 값이 동일한 행들을 하나의 그룹으로 묶습니다.
- **집계 함수**: 각 그룹 내의 행들을 대상으로 계산을 수행합니다.
  - `COUNT(*)`: 그룹에 속한 행의 총 개수
  - `SUM(...)`: 그룹 내 특정 수치 컬럼의 합계 (예: 주문별 총 결제 금액)
  - `AVG(...)`: 그룹 내 특정 수치 컬럼의 산술 평균 (예: 카테고리별 평균 메뉴 가격)

### Q8. 가장 복잡했던 쿼리와 해결 과정 (Q07, Q11)
- **Q07 (다중 조인)**: `orders`, `customer`, `order_item`, `menu` 4개 테이블의 관계를 바탕으로, 고객이 어떤 주문에서 어떤 메뉴를 몇 개 주문했는지 한눈에 파악하기 위해 외래키 관계를 따라 순차적으로 INNER JOIN을 연결하여 해결했습니다.
- **Q11 (주문별 총 결제액 집계)**: 주문 번호별로 `order_item`의 `(quantity * unit_price)`를 곱한 값을 `SUM()`으로 집계하여 각 주문의 최종 결제 금액을 도출했습니다.
